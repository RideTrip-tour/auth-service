# Регистрация и верификация

Этот документ описывает двухшаговый сценарий регистрации пользователя.

## Сценарий

1. Клиент отправляет `POST /api/auth/register` с `email` и `password`.
2. Сервис валидирует данные, но не создаёт пользователя сразу.
3. Вместо этого генерируется token для подтверждения и отправляется письмо на email пользователя.
4. Пользователь переходит по ссылке из письма.
5. Клиент отправляет токен на `POST /api/auth/verify`.
6. Сервис расшифровывает registration token, декодирует внутренний JWT и создаёт пользователя или выполняет смену email, если токен относится к этому сценарию.

## Токен регистрации

Токен формируется в `UserManager.on_before_register`.

Сначала формируется подписанный JWT, затем он шифруется перед отправкой в email.
JWT нужен для проверки срока жизни и целостности, шифрование скрывает payload
от клиента и промежуточных систем, где может оказаться ссылка.

В payload внутреннего JWT используются:

- `email`
- `hashed_password`
- `aud`
- `type=register`

Срок жизни verification token задаётся настройками. Для смены email используется
отдельный TTL `CHANGE_EMAIL_TOKEN_LIFETIME_SECONDS`, по умолчанию 1 час.

Для шифрования registration token используется `REGISTRATION_TOKEN_ENCRYPTION_SECRET`.
Если настройка не задана, сервис использует `JWT_SECRET`, но для production лучше
держать отдельный секрет и ротировать его независимо.

## Что делает `verify`

Метод `UserManager.verify`:

- для registration token расшифровывает внешний token;
- декодирует JWT с проверкой secret и audience;
- читает `type` из payload;
- если `type == register`, создаёт пользователя в БД;
- если `type == change_email`, проверяет pending-запрос в `email_change_requests`,
  запускает смену email и удаляет использованный токен;
- иначе считает токен невалидным.

## Поведение при ошибках

- невалидный, просроченный или токен с неверной audience возвращает `VERIFY_USER_BAD_TOKEN`;
- попытка подтвердить уже существующий email возвращает `VERIFY_USER_ALREADY_VERIFIED`.

## Формат ссылки

Ссылка на подтверждение строится через query-параметр `verify_token`.

Пример:

```text
{origin}/{lk_path}?verify_token=<encrypted-token>
```
